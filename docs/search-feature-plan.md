# Развитие локального поиска Lixun

Первой продуктовой функцией предлагается **подборка с цитатами**. Сегодня выдача помогает открыть отдельный объект. Подборка решает следующую задачу пользователя — собрать несколько найденных фрагментов, проверить их и использовать вместе. Она полезна автономно и даёт понятную границу доступа для будущего анализа документов. Облачная интеграция в опубликованную дорожную карту 1.x не входит. Внешний адаптер можно проверить отдельным экспериментом. [Дорожная карта проекта](../README.md#roadmap)

## Возможности без модели

| Что реализовать | Зачем пользователю | Первый проверяемый результат |
| --- | --- | --- |
| **Подборка с цитатами** | Сохранить фрагмент письма, страницу PDF и абзац документа, затем вернуться к оригиналам. | Выбрать три результата с клавиатуры, экспортировать выдержки в Markdown и открыть каждую у источника. Если источник изменился, показать это. |
| **«Почему файл не найден?»** | Отличить исключение правилами от ошибки чтения, ожидания OCR и отсутствия текстового слоя. | Расширить существующую `check-exclude`. Показывать решение индексатора, совпавшее правило и последний известный этап обработки. Проверка сама не ставит файл в очередь. |
| **Приватный сеанс и «забыть»** | Один раз поработать с чувствительной темой и управлять уже накопленной историей. | Видимый режим на время открытия лаунчера. По завершении и перезапуске отсутствуют запросы, клики и связи персонализации этого сеанса. Для очистки показывать затрагиваемые хранилища и период. |
| **Статус и восстановление источника** | Узнать, почему обновились файлы, но всё ещё нет свежих вложений. | В существующей панели показать экземпляр источника, последнюю удачную синхронизацию, очередь и последнюю ошибку. Дать повторить только его задание с индикацией завершения. |
| **Связанные версии и вложения** | Перейти от сохранённого файла к письму, из которого он получен, и сравнить две редакции. | Сначала связывать по явной связи источника и точному совпадению содержимого. Показывать основание связи и различать одинаковые копии и предполагаемые версии. |
| **Возврат к рабочей теме** | Восстановить материалы, с которыми человек работал вчера. | Начать с ограниченной сессии из вручную выбранных файлов и писем. Затем проверить пользу автоматических подсказок по времени и подтверждённым связям. Это первый шаг к уже запланированному восстановлению рабочего пространства. |

У подборки есть техническая предпосылка. Ссылка на результат должна уметь указать точное место и версию содержимого. Источник предоставляет непрозрачный идентификатор, доступный адрес фрагмента и способ перехода. Страница, абзац или конкретное письмо определяются плагином. Общий интерфейс отображает ссылку и делегирует переход. Источник без адресации фрагмента открывает документ целиком, а интерфейс показывает доступную точность. [Границы плагинов](../AGENTS.md)

## Где пригодится языковая модель

| Задача | Какой подход проверить первым | Что увидит человек |
| --- | --- | --- |
| **Задать вопрос по подборке** | Один запрос к выбранной локальной модели или явно включённому провайдеру. В контексте только выбранные выдержки и их ссылки. | Ответ на вопрос «Какой срок указан в этих письмах?» с цитатой, переходом к месту и пометкой, если срок не указан. |
| **Сравнить редакции** | Сначала обычное локальное сравнение текста. На запрос «Что изменилось по существу?» модель объясняет отмеченные отличия. | Таблица «было / стало» с обеими цитатами. Разночтения и пропуски видны даже при ошибке интерпретации. |
| **Восстановить ход решения** | Здесь оправдан агентный цикл. Искать внутри разрешённой подборки, читать фрагменты, уточнять запрос и проверять дату или противоречие. | Хронология «предложили → изменили → подтвердили». У каждого события источник, дата исходного сообщения и статус подтверждения. |
| **Найти документ на другом языке** | По явной команде предложить переводы и синонимы, затем выполнить их локально. Сравнить с существующим семантическим поиском на RU/EN/ZH. | Пользователь видит варианты запроса и найденные оригиналы. Эффект измеряется тем, нашёлся ли правильный документ. |

## Как подключать внешний агентный инструмент

1. **Выделить отдельную программу с локальным MCP-интерфейсом через stdio.** Клиент запускает адаптер по требованию. Lixun передаёт ему конкретную подборку и срок её действия. Лаунчер, демон и поисковый индекс не зависят от установленной агентной среды. Необходимые новые сообщения IPC проектировать после стабилизации формата. [План исправлений](audit-remediation-plan.md)
2. **Дать два инструмента.** Поиск возвращает краткие результаты в пределах подборки. Чтение возвращает ограниченный фрагмент и ссылку. Идентификаторы действуют только в данном сеансе. Границы чтения, актуальность документа, ограничения длины и отзыв доступа проверяет Lixun на каждом обращении. Для документов, которые нельзя адресовать, заранее показать ограничение.
3. **Управлять передачей у источника данных.** Для пилота использовать изолированный профиль клиента с доступом только к этим двум операциям. Исключить общий сокет управления, произвольные пути, запуск программ и изменение документов. Для внешнего провайдера до передачи показать получателя, вопрос и объём разрешённых выдержек. Поиск и результаты тоже могут раскрывать содержание. Учесть хранение истории внешним клиентом, очищать временный контекст согласно выбранному режиму. Режим «только локально» проверять с отключённой сетью. В приватном сеансе внешний доступ закрыт.
   У локального процесса обычно есть права пользователя. Для пилота на личных документах изолировать процесс внешней среды средствами ОС и исключить прямой доступ к домашнему каталогу и штатному сокету демона. Проверить это из запущенного профиля. Одного ограничения списка инструментов для такой гарантии недостаточно.
4. **Обрабатывать документ как материал для цитирования.** Найденный текст не меняет список инструментов и разрешений. Проверять ссылки в ответе по реально выданным фрагментам. После изменения или удаления источника показывать устаревшую ссылку. Если подтверждения нет, отвечать «В выбранных материалах подтверждения нет».
5. **Ограничить многократные обращения.** Предлагаемые стартовые пределы пилота — три раунда инструментов и явный лимит общего объёма текста на вопрос. Измерять время первого ответа, полную задержку и стоимость завершённой задачи. Отмена останавливает дальнейшие обращения. Обычный ввод в лаунчере вызывает только локальный поиск.

## Порядок пилота и решение о продолжении

1. Собрать 30 воспроизводимых задач на синтетических письмах, PDF и двуязычных документах. Добавить противоречащие редакции, вопросы без ответа, отозванный доступ и устаревшие ссылки. Разметить правильный факт и место, где он подтверждён.
2. На одной и той же подборке сравнить три режима — ручной поиск с цитатами, один запрос модели и агент с двумя инструментами. На задаче «найти согласованный срок, прочитать поправку, показать подтверждение» измерить долю верных ответов с верной ссылкой, время пользователя до проверки, число переданных фрагментов и стоимость. Локальный и внешний провайдеры оценивать раздельно.
3. Предлагаемые условия следующего этапа — не менее 90% проверяемых утверждений подтверждены указанными фрагментами, каждая принятая ссылка открывает правильный источник, закрытые материалы недоступны во всех контрольных случаях. Измерить также долю правильно отмеченных вопросов без ответа. Одного качества ссылок недостаточно для выбора агентного режима. Он должен дополнительно решать многошаговые задачи, которые не решил вариант с одним запросом, при приемлемых для пользователя времени и цене.
4. В основной продукт первой переносить самую простую выигравшую функцию. Если сопоставимые ответы уже даёт один запрос по выбранным цитатам, его достаточно для кнопки «Спросить по подборке». Внешний интерфейс останется доступным для отдельных многошаговых сценариев. Решение об облачной функции в основной ветке 1.x потребует явного пересмотра текущей дорожной карты.
